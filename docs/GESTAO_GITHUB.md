# Gestão do Projeto no GitHub

## Objetivo

O GitHub deve demonstrar evolução real e organizada do trabalho, não apenas servir como depósito final de ficheiros.

## Princípios

- Commits correspondem a alterações reais.
- Mensagens de commit são claras e específicas.
- Issues representam tarefas verificáveis.
- Não se altera código apenas para criar histórico artificial.
- A documentação acompanha a evolução real.
- O Kanban do Notion funciona como visão de gestão; o GitHub como histórico técnico.

## Convenção de commits

Exemplos:

- `docs: add project README`
- `docs: add architecture documentation`
- `test: document acceptance criteria`
- `feat: add reservation validation`
- `fix: prevent duplicate laptop assignment`

## Processo recomendado

1. Criar ou atualizar uma Issue.
2. Fazer a alteração real.
3. Testar.
4. Fazer commit com mensagem clara.
5. Associar a Issue quando aplicável.
6. Atualizar o Kanban.
7. Fechar a Issue apenas quando os critérios estiverem cumpridos.

## Estado atual

O repositório foi criado na fase final de organização do projeto. Não serão fabricados commits que pretendam representar trabalho passado. A partir deste ponto, a evolução ficará registada de forma real.
